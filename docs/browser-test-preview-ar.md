# تشغيل واجهة اختبار محلية معزولة

تم تجهيز الطريقة فقط. لم يبدأ خادم Next.js ولم نفتح متصفحًا أو اتصال قاعدة في هذه المهمة، ولم نغير إعدادات Google OAuth أو ملفات أسرار الاختبار. التطبيق الأصلي وتسجيل الدخول Google الأصلي لم يتغيرا.

## ما الذي يفعله المشغّل؟

الأمر `npm run preview:test` يشغّل `scripts/preview-test-site.cjs` بعد تجهيز إعدادات OAuth التجريبية والحصول على الموافقة.

- يقرأ `.env.test.local` وحده عبر dotenv.parse ويتحقق من قاعدة nyba_test والمضيف المؤكد وTLS وتأكيد المشروع.
- لا يقرأ .env أو .env.local، ولا يرث DATABASE_URL أو أسرار OAuth أو OpenAI أو NODE_OPTIONS من بيئة الطرفية. يمرر متغيرات محددة فقط إلى Next.
- قبل تشغيل الخادم يجري فحص اسم القاعدة الحالي بمعاملة قراءة فقط، ويعيد فحص إعداد الهدف. هذا الاتصال يحدث عند التشغيل الفعلي فقط، وليس عند أمر التحضير.
- يجهز نسخة مؤقتة من app وlib وauth والملفات اللازمة داخل مجلد مستقل، دون ملفات .env أو سجلات البناء السابقة. يشير node_modules إلى الاعتماديات المثبتة؛ ملفات التطبيق والإعداد نفسها نسخ مستقلة.
- يولّد app/globals.css داخل النسخة المؤقتة بمحوّل Tailwind المثبت، مع فحص مجلد النسخة لاستخراج أصناف الواجهة. هذه معالجة مستقلة للمعاينة؛ أصبح بناء المشروع الأساسي يستخدم Webpack وPostCSS رسميًا أيضًا، بينما النسخة المؤقتة تتلقى CSS مولّدة مسبقًا. تبقى CSS الأصلية كما هي.
- يشغّل Next من النسخة المؤقتة على 127.0.0.1 والمنفذ 3100 باستخدام Webpack. يستخدم NODE_ENV=development المعتاد؛ العزل بالمجلد والبيئة المحددين، وليس اعتمادًا على NODE_ENV=test الذي قد يظل يقرأ .env.
- عميل Prisma داخل النسخة المؤقتة يستخدم NYBA_TEST_DATABASE_URL صراحة ويعيد التحقق من المسار والمضيف. لا يرجع إلى اتصال افتراضي.
- يستبدل خدمة الترجمة في النسخة المؤقتة بترجمة وهمية موسومة للاختبار، دون استيراد OpenAI أو تمرير مفاتيحه. زر الترجمة لا يختبر جودة أو اتصال OpenAI.
- يجعل جلب RSS يعيد قائمة فارغة: الزر لا يجلب أخبارًا حقيقية، وتبقى الأخبار الوهمية الموجودة في قاعدة الاختبار متاحة. اختبار شبكة RSS ليس ضمن هذه المعاينة.
- يستخدم خط النظام بدل تنزيل Cairo من Google Fonts؛ لذلك قد يختلف شكل الخط عن الموقع الفعلي. بقية الواجهة من ملفات المشروع الحالية.
- يحتفظ بتسجيل الدخول Google الحقيقي، ولا ينشئ تجاوزًا للتوثيق أو مديرًا افتراضيًا. يتطلب مفتاح جلسة وعميل Google تجريبيين وبريد مدير محددًا.
- لا ينسخ prisma.config.ts أو Migrations إلى النسخة، ولا يشغّل Prisma CLI أو npm scripts من داخلها.
- لا يطبع مخرجات Next/Auth الخام لحجب بيانات الاتصال والرموز؛ عند تعثر التشغيل قد تحتاج مراجعة تشخيص آمنة مستقلة.
- عند Ctrl+C يحذف النسخة المحلية المؤقتة فقط. لا يحذف أي خبر من القاعدة. التعديلات التي تجرينها من لوحة الإدارة تُحفظ فعلًا في nyba_test وتبقى بعد إيقاف المعاينة.

## إعدادات تسجيل الدخول المطلوبة — لم ننشئها

يلزم إعداد OAuth اختبار مستقل دون المساس بعميل الإنتاج، ويفضل داخل Google Cloud project مخصص للاختبار. الخطوات التالية شرح لخطة تحتاج موافقتك قبل تنفيذها:

1. إنشاء/اختيار Google Cloud project تجريبي مستقل، ثم إعداد Google Auth Platform/Consent باسم واضح للاختبار.
2. إبقاء النشر Testing وإضافة حساب Google الذي ستستخدمينه كمدير اختبار ضمن Test users إن كان نوع الجمهور External. لا نستخدم إعداد OAuth الإنتاجي.
3. إنشاء OAuth Client من نوع Web application لهذا المشروع التجريبي.
4. ضبط Authorized JavaScript origin على `http://localhost:3100` إن طُلب، وAuthorized redirect URI بالضبط على `http://localhost:3100/api/auth/callback/google`.
5. حفظ Client ID وClient Secret في .env.test.local فقط تحت الاسمين TEST_AUTH_GOOGLE_ID وTEST_AUTH_GOOGLE_SECRET، دون إرسالها بالمحادثة أو عرضها في الطرفية.
6. إدخال بريد حساب الاختبار في TEST_ADMIN_EMAIL. يستخدم المشغّل هذا البريد لتكوين ADMIN_EMAIL في العملية المؤقتة، ويظل شرط Google email_verified وتطابق البريد في auth.ts فعّالًا.
7. توليد TEST_AUTH_SECRET جديد مستقل لا يقل عن 32 حرفًا وحفظه مباشرة في الملف دون طباعته. لم نولّد سرًا أو نضيف متغيرات OAuth إلى الملف الآن، لأن ذلك ينتظر موافقتك.

المتغيرات التي ستحتاج إضافتها بنفسك لاحقًا داخل الملف المستبعد من Git هي:

- TEST_ADMIN_EMAIL
- TEST_AUTH_GOOGLE_ID
- TEST_AUTH_GOOGLE_SECRET
- TEST_AUTH_SECRET

المشغّل يرفض بدء الخادم إذا كانت ناقصة أو غير صالحة، ولا يستخدم متغيرات الإنتاج كبديل. لا يمكن إثبات نجاح تسجيل الدخول الحقيقي قبل إنشاء هذا العميل وتجربة المتصفح. وجود القيم واجتياز فحص الشكل لا يثبت صحة أسرار OAuth أو إعداد callback.

مراجع رسمية:
- [Auth.js: Google callback](https://authjs.dev/reference/core/providers/google)
- [Google: إعداد عميل OAuth لتطبيق ويب ومطابقة redirect URI](https://developers.google.com/identity/protocols/oauth2/web-server)
- [Google: فصل بيئات الاختبار عن عملاء الإنتاج](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)

## طريقة التشغيل بعد الموافقة واستكمال OAuth

من جذر المشروع:

```sh
npm run preview:test:check
```

هذا فحص محلي فقط: يتحقق من هدف القاعدة ويجهز نسخة مؤقتة ثم يحذفها دون خادم أو اتصال قاعدة أو Google. يطبع أسماء متغيرات OAuth الناقصة فقط.

بعد نجاح الإعداد وموافقتك على التشغيل الفعلي:

```sh
npm run preview:test
```

افتحي `http://localhost:3100`، ثم `/login` وسجلي الدخول بحساب مدير الاختبار. استخدمي نافذة خاصة لتجنب تداخل ملفات جلسات localhost مع تطبيقات محلية أخرى. إذا كان المنفذ مشغولًا يتعين إيقاف المعاينة ومراجعة منفذها وcallback معًا؛ لا تغيّري منفذ الأمر عشوائيًا.

استخدمي الأخبار الوهمية الموجودة: راجعي الأصل، وجربي Mock الترجمة على مسودة ذات أصل، واحفظي العربية وأرسلي للمراجعة ثم اعتمدي وانشري. خبر الاختبار القديم بلا أصل يبقى قابلًا للتحرير اليدوي؛ زر ترجمته معطل. إعادة تحميل الصفحة العامة يجب أن تعرض المنشور فقط. لا نحتاج لإدخال بيانات إضافية أو Migration.

توقفي بـ Ctrl+C. لا تستخدمي npm run dev أو start المعتادين لهذه التجربة، ولا تنسخي بيانات الاختبار إلى ملفات إعداد الإنتاج. إذا أردت انعكاس تغييرات الكود المحلي أثناء الجلسة أوقفي المشغّل وأعيدي تشغيله؛ النسخة مستقلة ولا تتابع تحرير ملفات المصدر الأصلية.

## نتيجة التحضير

- نجح preview:test:check دون اتصال: أُنشئت النسخة المؤقتة وأزيلت بنجاح.
- وجد الفحص أن متغيرات OAuth الأربعة أعلاه غير مجهزة؛ لم تُعدّل تلقائيًا.
- تم اختبار أن المشغّل لا يرث DATABASE_URL أو OPENAI_API_KEY أو AUTH_SECRET أو NODE_OPTIONS من البيئة الأصلية.
- لم يُختبر تسجيل الدخول الحقيقي أو العرض بالمتصفح بعد، ولم يبدأ الخادم.
- لا تعديل قاعدة ولا Migration أو db push أو Push أو Merge أو Deploy.


## إصلاح CSS في مشغّل المعاينة

السبب وقت اكتشاف المشكلة: تحميل globals.css نفسه كان ناجحًا، لكن تشغيل Webpack لم يكن ينفذ قاعدة @tailwindcss/turbopack التي كانت في next.config.ts، ولم يكن يوجد postcss.config أو @tailwindcss/postcss بديل. أُضيف PostCSS الرسمي لاحقًا عند تجهيز إصدار النشر. لذلك وصلت CSS الأساسية دون أصناف Tailwind: ظهر display:block بدل grid وخلفية الوضع الداكن الأساسية.

الإصلاح محدود للمشغّل: compilePreviewCss يولّد CSS كاملة داخل النسخة المؤقتة باستخدام المحوّل المثبت @tailwindcss/turbopack عبر واجهة loader، قبل بدء Next. يحدد base بمجلد النسخة حتى يشمل فحص الأصناف الصفحة والإدارة، ويوقف التحضير إذا لم تظهر أصناف grid والحواف. لا تثبيت حزم أو تعديل إعداد الإنتاج أو globals.css أو الصفحة الرئيسية الأصلية. جرى توليد CSS للنسخة الجارية أيضًا لتصحيح العرض فورًا.

نتائج التحقق:
- في المتصفح عاد display:grid والحواف 24px للبطاقة، واستعادت القائمة والبطاقات ألوانها ومسافاتها.
- طلب CSS وثلاثة موارد JavaScript رجعت 200؛ CSS الناتجة تتضمن grid وrounded-3xl ولا تحتوي @theme أو @tailwind غير معالجة.
- لم تسجل الصفحة أخطاء أو تحذيرات أثناء الفحص.
- نجحت الاختبارات المحلية الاثنا عشر وTypeScript وESLint وgit diff --check.
- اختبار الانحدار يولّد نسخة فعلية ويفحص أصناف الشبكة والحواف والألوان ونقاط الاستجابة وinput-style، ويثبت تطابق الصفحة الرئيسية وnext.config مع الأصل وعدم تغيير ملفات المصدر.
- لا تعديل قاعدة أو Migration أو db push أو Push أو Merge أو Deploy. طلبات المتصفح العامة تقرأ أخبار الاختبار الموجودة فقط.
